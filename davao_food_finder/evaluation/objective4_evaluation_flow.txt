DAVAO FOOD FINDER
OBJECTIVE 4: PRICE, THEMATIC INTENT, ITERATIVE REFINEMENT, AND USABILITY

Purpose
-------
This note explains how the project represents user-defined price and thematic
criteria, how the autonomous loop can repair a draft shortlist, how the
benchmark scores those behaviors, and what human usability evidence is
currently available.

1. FILES AND THEIR ROLES
------------------------

evaluation/ground_truth.json
  Contains test queries, split assignments, benchmark constraints such as
  max_price_php, keywords_any and ambiance, and the expected relevant venue
  names/grades. It defines what each benchmark case asks the system to do.

src/search.php
  Parses a user's query into structured intent, including numeric price
  ceilings, cuisine/dishes, ambiance, thematic tags, and conversational
  context. It extracts explicit peso amounts from evidence, uses review
  signals, ranks candidates, and applies numeric price filtering.

src/web_reasoner.php
  Contains critiqueSinglePlace() and runAutonomousRefinementLoop(). The
  critic examines draft venues for conditions such as verified price
  violations, wrong location, category/dish mismatch, closures, hours,
  dietary restrictions, and previously excluded venues. If repair is needed,
  the loop can re-retrieve candidates and score the revised list.

evaluation/metrics.php
  Computes benchmark constraint outcomes. It checks city, cuisine/keywords,
  area, numeric price, budget tier, dietary restrictions, ambiance, and other
  fields when those constraints are present in a case.

evaluation/run_evaluation.php
  Runs cases/configurations, records the response and loop telemetry, then
  aggregates numeric price compliance and loop statistics. The file hash
  differs from the version recorded by dev_grid.json.

evaluation/usability.php
  Defines six participant tasks, computes the standard 10-item SUS score,
  stores real participant submissions, and aggregates task completion,
  time, perceived relevance, and price/source trust. It does not fabricate
  participant data.

evaluation/results/dev_grid.json
  Stores the development run's manifest, per-configuration summary,
  participant-study status, and detailed results by case/trial. Look in
  summary for aggregate metrics and detailed_runs for case-level telemetry.

evaluation/RESEARCH_PROTOCOL.md
  Defines the planned objective-to-metric mapping and the intended human
  study. Compare its formal metric definition with the implementation before
  making a strict compliance claim.

2. FLOW FROM USER REQUEST TO REPORTED RESULT
--------------------------------------------

Step A - Represent the criteria.
  The ground-truth case records what the query means: for example, a numeric
  maximum price, food category, location, thematic preference, and relevance
  labels.

Step B - Parse the natural-language query.
  search.php extracts a numeric ceiling such as "under PHP 180" into
  max_price_php = 180. It also maps thematic phrases such as "quiet study"
  or "Wi-Fi and sockets" into structured intent tags.

Step C - Retrieve and rank candidates.
  Candidate scores use cuisine/category matching, review evidence, price
  evidence, ambiance signals, and thematic signals. Some preferences are
  ranking boosts rather than absolute exclusion rules.

Step D - Critique the first shortlist.
  web_reasoner.php audits top candidates. When it detects a rule violation
  or insufficient compliant candidates, it can perform Pass 2 retrieval and
  build a repaired shortlist.

Step E - Independently score the result.
  metrics.php compares the final recommendations with benchmark constraints.
  run_evaluation.php records price compliance, loop telemetry, ranking
  quality, and latency in the per-case result.

Step F - Measure human experience separately.
  usability.php collects task completion, time-on-task, perceived relevance,
  price/source trust, and SUS responses from real participants. These scores
  do not come from the automated benchmark.

This is the input specification. The evaluator also has relevance labels for

EXAMPLE 2 - Parse and apply a numeric ceiling
Parser excerpt from src/search.php:

  } elseif (preg_match('/\b(?:under|below|max(?:imum)?(?:\s+of)?|up\s+to|within|less\s+than|at\s+most|not\s+more\s+than|ceiling(?:\s+of)?|budget(?:\s+of)?)\s*(?:₱|php\s*|p\s*)?(\d{2,4})\s*(?:pesos|php)?\b/iu', $rawLower, $pm)) {
      $val = (float)$pm[1];
      if ($val >= 35 && $val <= 5000) {
          $maxPricePhp = $val;
      }
  }

Price-filter excerpt from src/search.php:

  $vp = getVerifiedPlacePricePhp($item);
  if ($vp !== null) {
      if ($maxPricePhp !== null && $vp['median'] > $maxPricePhp) {
          continue;
      }
  }

For prices that cannot be verified, the current filter can use review signals
to reject a venue marked repeatedly expensive under a tight ceiling. It does
not automatically prove an unknown price is within budget. The UI can label
price evidence as review-reported or live web evidence; that provenance is
different from a guaranteed menu price.

EXAMPLE 3 - Thematic intent affects ranking
Excerpt from src/search.php:

  if (in_array('quiet_study', $ambiance, true)) {
      if ($quietCount > 0) {
          $foodScore += ($isCafe ? 8.0 : 3.0) + min(4.0, $quietCount * 2.0);
      }
      if ($wifiCount > 0) {
          $foodScore += 4.5 + min(3.0, $wifiCount * 1.5);
      }
  }

Meaning:
  - The system parses thematic phrases and can boost candidates supported by
    review signals.
  - In the inspected code, thematic evidence is generally used to rank
    candidates. The autonomous critic does not impose a universal hard
    pass/fail rule for every ambiance/thematic tag.
  - metrics.php can evaluate an explicit benchmark ambiance constraint when
    that constraint is present. The dev_grid development cases do not provide
    a standalone thematic-usability result.

EXAMPLE 5 - Automated price score versus human usability score
Excerpt from evaluation/metrics.php:

  'numeric_price_compliant' =>
      $hasPriceCeiling
      ? (($dimScores['max_price_php'] ?? 0.0) >= 0.8
          && $verifiedPriceHits >= 1)
      : null,

This is the implementation's explicit price-compliance rule. In the
development split, the selected configuration passed its single numeric
price-ceiling case, so the saved rate is 1/1 = 100%. This does not mean all
five venues had verified prices.

The human instrument in evaluation/usability.php uses the standard SUS
scoring transformation:

  odd SUS items:  response - 1
  even SUS items: 5 - response
  final SUS:      sum of contributions * 2.5

It also asks participants to perform UT2 (numeric price ceiling) and UT3
(thematic keywords/ambiance), then records task completion, time, relevance,
and trust ratings. The report currently says:

  "participant_count": 0,
  "sus_ci95": null,
  "mean_perceived_relevance_1_5": null,
  "mean_price_source_trust_1_5": null

Therefore, no empirical SUS, human relevance, or participant trust result is
available yet.

4. HOW TO STATE THE FINDINGS RESPONSIBLY
----------------------------------------

What the current dev report supports:
  - PC004 is a concrete example where the loop detected an over-ceiling
    candidate, re-retrieved, and recorded a passing final price check.
  - The selected configuration's stored numeric price-compliance rate is
    100% for the one explicit price-ceiling case in this dev split.
  - The report records 2 detected and 2 repaired violations across 13
    loop-enabled requests; average initial compliance is 95.9% and final
    compliance is 100%.

What it does not yet support:
  - A general claim that all price recommendations are verified below budget.
  - A broad estimate of price-ceiling success from one development case.
  - A human usability, perceived relevance, or trust conclusion (n = 0).
  - A dedicated development-split result for thematic preferences such as
    quiet study, Wi-Fi, or romantic ambiance.

Additional audit caution:
  In this report, the aggregate loop telemetry records 2 violations detected
  and 2 repaired, while the nested cause_rates reports zero violation_repair
  requests. These fields do not reconcile from the saved summary alone. Avoid
  using the cause_rates breakdown until it is reconciled against the exact
  source version and per-case detailed_runs.

5. PRESENTATION SUMMARY
-----------------------
Objective 4 is partly supported by automated evidence: the selected
development configuration passed one explicit numeric price-ceiling case,
and PC004 shows a concrete critique-and-retrieval repair. The implementation
also parses and ranks thematic signals, but the development report does not
provide a separate human-tested thematic relevance score. The usability
instrument is ready to collect such evidence, but no participants have
submitted responses. The stored development result should therefore be
reported as preliminary algorithmic evidence, not as proof of overall
usability or universal strict adherence.
